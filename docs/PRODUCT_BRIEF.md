# Aftertrace：选择动机与首个实验

日期：2026-09-08。负责人：Codex Improvement Lab 产品负责人任务。

## 2026-09-08 开发后的决定

已运行的首个对照表明，VizTracer 加一段独立查询脚本即可恢复演示中的历史值。因此停止自建记录引擎，把 Aftertrace 收窄为读取 VizTracer JSON 的实验性查询集成。现已实现 inspect/history/first/calls 和简短 Skill；下文的完整记录器设想保留为选题历史，不代表当前能力。

用户已授权全权推进及 GitHub/X 操作。可以公开经过验证的集成预览，用于收集实际问题；独立产品的 M0 门槛保持未通过。8 个库的兼容性检查不替代 8 个调试任务和 4 个 Agent 负例。详见 [下一阶段门槛](NEXT_STAGE.md)。

## 直接价值

Agent 调试一个 Python 任务时，最终异常现场可能已经丢失关键中间值。Aftertrace 的拟定使用单元是：记录用户选择的运行范围，随后通过几个精确查询取得已捕获的历史，减少临时改源码和重跑。

它不推断未捕获的数据，不自动证明根因，不作为验收证据管理平台。最初只有一个同步标量机制探针；当前交付范围见上方开发决定。

## 拟定首版

- 同步 Python/pytest，用户选择的模块与捕获预算。
- 运行、测试和函数调用的稳定标识；绑定捕获时的源码。
- 查询已观察到的首次条件匹配、值变化、特定调用历史。
- 返回严格 JSON，以及采样、截断、缺失或不支持的范围。
- 默认本地保存；事后查询不运行任意 Python；不需要额外模型 API。
- 一份短 Skill，仅在需要历史运行信息时触发。简单报错、静态语法问题等应跳过。

以上均为拟定功能，不是已经存在的命令。先判断是否可复用 VizTracer/Birdseye 等底座，避免重建通用 tracing 引擎。

## M0：必须满足的选择门槛

选择 8 个公开仓库中的非玩具调试任务及 4 个负例，冻结基线、捕获范围、结果检查器与成本判据。历史重放、合成场景和现场内部任务分开报告。

基线：pytest -l/PDB；mcp-debugger；VizTracer + 合理的可复用查询脚本；适用时加入 Birdseye。基线可使用自己的标准文档与合理辅助脚本，不能故意少记录关键变量。

记录结果正确性、程序重跑、临时源码修改、工具往返、记录成本、磁盘量、总墙钟耗时。实际模型用量不可得时记 unavailable，不用字节数伪装 token 或人工省时。

继续条件：正确性不低于基线，至少两类任务获得实际调试成本改善，并在不点名的适用任务中出现正确自主选择。阈值在运行前固定；发现无关任务误激活，也计为产品成本。

如果现有工具加少量脚本同样好，或捕获成本抵消收益，停止独立产品路线，保留实验与可贡献的集成。

## 为什么不继续 JobPort

成熟作业工具已覆盖许多基本动作，新增统一接口未形成足够强的选择理由。Aftertrace 的动机更直接地指向缺失信息，但仍必须经过强基线验证，不能因这个描述更动听就跳过验证。

## 独立性与后续

本项目不依赖 Proofline 的验收模型，不强制导出 Workprint Profile。与既有主线保持独立仓库和评价。

原计划是 M0 后开发独立 CLI/插件。此次依据反证改为可安装的 VizTracer 查询集成预览，不开发独立 recorder 或完整插件。对外不得把这次集成的公开分发解释为独立产品 M0 通过。公开发行仍由 Lab 负责人统筹。
